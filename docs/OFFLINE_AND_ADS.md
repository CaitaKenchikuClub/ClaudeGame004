# オフライン対応・広告導入：課題と設計上の注意点

## オフライン対応

オフライン動作は将来の必須要件。経路は 2 つあり、両方を見据える。

### A. アプリ（Capacitor）

Web 資産はアプリに同梱されるため、**外部リソースに依存しない限り自動的にオフラインで動く**。

現状の外部依存は Google Fonts のみ（読めない場合は端末フォントで表示され、ゲームは動く）。見た目を揃えるにはフォントの同梱が必要。

必要なのは次の規律のみ：

- フォント・ライブラリ・画像・音声を CDN から読まず、リポジトリ内（`assets/` 等）に置く
- ネットワークが必要な機能（ランキング、広告など）は、失敗してもゲーム進行を止めない作りにする
- `navigator.onLine` は目安に過ぎないので、通信処理は必ずタイムアウトとエラー処理を付ける

### B. ブラウザ（GitHub Pages / PWA）

ブラウザ版をオフライン化するには Service Worker が必要（未実装）。追加時の課題：

- `manifest.webmanifest` とアイコン（192px / 512px）の用意
- Service Worker のスコープは配置ディレクトリ以下になる。`./sw.js` をリポジトリ直下に置き、相対パスで登録すれば Pages のサブパスでも動く
- 現状は index.html（約 6.2MB）と bgm.mp3（約 3.1MB）の 2 ファイルなので、キャッシュ対象は少なく済む（BGM は `fetch` で読むため、Service Worker でキャッシュすればオフラインでも鳴る）
- キャッシュするファイル一覧の管理と、更新時のキャッシュ破棄（バージョン番号付きキャッシュ名）。ビルド工程が無いため、ファイル追加時にリストを更新するルールか、生成スクリプトが必要
- **Capacitor 内では Service Worker を登録しない**（同梱資産と二重管理になり更新トラブルの原因になる）。`window.Capacitor?.isNativePlatform()` で判定して分岐する
- 古いキャッシュが残って新バージョンが反映されない問題への対策（更新検知 → 再読み込み案内）

## 広告

広告配信サービスへの登録・広告 ID の設定は行っていない。導入は指示があった段階で行う。

### 現在の設計

- ゲームコードは `src/ads.js` のインターフェース（`showBanner` / `showInterstitial` / `showRewarded` 等）だけを呼ぶ。現在は何もしないスタブ
- 導入時は実装だけを差し替える（例：アプリは AdMob の Capacitor プラグイン、ブラウザ版は広告なし or Web 向け広告）

### 導入時の注意点

- **広告 ID は秘密情報ではないが、テスト ID と本番 ID を取り違えない**。開発中は必ずテスト広告 ID を使う（本番 ID で自分でクリックするとアカウント停止のリスク）
- **オフライン時**：広告が読み込めなくてもゲームが止まらないこと。リワード広告は「読み込めない時はボタンを無効化」する
- **一時停止**：インタースティシャル・リワード表示中はゲームループと音声を止め、閉じたら再開する
- **報酬付与**：リワードは SDK の「報酬獲得」コールバック時のみ付与（`granted` で判定）
- **レイアウト**：バナー領域を safe-area と合わせて確保し、ゲーム画面や操作ボタンと重ねない（誤タップ誘導はポリシー違反）
- **表示頻度**：プレイ中の割り込みを避け、ゲームオーバー後などの区切りで表示する
- **プライバシー**：GDPR / 各国規制の同意取得（UMP 等）、ストアのデータセーフティ申告、プライバシーポリシーの用意が必要
- **子ども向け判定**：対象年齢によって広告設定（COPPA / Families ポリシー）が変わるため、ターゲット層を早めに決める
- **Web 版の広告**：GitHub Pages 上での広告掲載は利用規約や広告サービス側の審査条件を確認したうえで判断する
